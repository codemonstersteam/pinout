# Бэклог экосистемы pinout (верхнеуровневый)

Платформенный план развития. Детальные пер-сервисные бэклоги ведутся в `docs/design/<slug>/backlog.md` каждого репозитория по скиллу `program-design`. Здесь — эпики, зависимости и порядок.

Источник истины концепта — [`README.md`](./README.md). Зафиксированные решения по развилке pinout-openapi:

1. Заглушки **и** сценарии компонентных тестов потребителя выводятся из master-спеки поставщика (слой методологии).
2. `pinout-openapi` MVP = **чистая функция** `consumer OpenAPI` vs `provider master OpenAPI`, симметрично `pinout-asyncapi` (слой инструмента).
3. Генерация сценариев из спеки поставщика = доработка скилла `component-tests` в `service-template` (upstream), не часть инструмента.

## Карта зависимостей

```
E4 service-template (скилл component-tests от спеки поставщика)  ── методология, независимо
E0 pinout-asyncapi: формат отчёта под netlist ──┐
E1 pinout-openapi: чистая функция валидации ────┼──► E2 pinout-netlist: граф + приём отчётов
                                                 └──► E3 pinout-cli (единый фронт)
```

Порядок: **E1 → E0 → E2 → E3**; **E4** параллельно. E1 первый, т.к. даёт второй валидатор и фиксирует общий формат отчёта, под который затем подгоняется E0 и который потребляет E2.

## E0 — pinout-asyncapi: подготовка к интеграции с netlist

**Статус:** ✅ инструмент работает; доработка под экосистему.
**Цель:** привести вывод async-валидатора к единому структурированному отчёту, который потребляет `pinout-netlist`.
**Репозиторий:** `../pinout-asyncapi`. Детальный план доработки: [`pinout-asyncapi/docs/integration-netlist.md`](../pinout-asyncapi/docs/integration-netlist.md).

- [x] Общий формат отчёта зафиксирован в `pinout-openapi` (канон [report-format.md](../pinout-openapi/docs/report-format.md)); async подстраивается под него.
- [ ] Привести существующий `compatibility_report.json` к общему формату.
- [ ] Команда/флаг выгрузки отчёта для netlist (stdout/файл).
- [ ] Не ломать текущий CLI и exit codes.

**DoD:** async-валидатор отдаёт отчёт в общем формате; зелёный CI; описано в README async-репо.

## E1 — pinout-openapi: чистая функция валидации соответствия контрактов (MVP)

**Статус:** 📋 проектирование завершено (этап 2): репозиторий создан, пакет `docs/design/contract-validate/` готов, ждёт handoff-аппрува. Решения оператора: парсер `kin-openapi`; канон формата отчёта определён здесь; поставщик `spec_url`+`spec_path`.
**Цель:** MVP по `intent.md` — функция сравнения OpenAPI потребителя и master-OpenAPI поставщика, симметрично async по конфигурации (`contract-tests.yaml`) и выходу.
**Репозиторий:** новый `pinout-openapi` (рядом с async). Скиллы — из `service-template`.

Объём MVP (валидация одной пары операций):
- [ ] Парсер OpenAPI 3.x (или зрелая библиотека — honest reuse) в рабочую структуру.
- [ ] Конфиг `contract-tests.yaml`, симметричный async (consumer spec_path, provider spec_url=master, перечень используемых операций).
- [ ] Чистая функция: для операции потребителя найти операцию поставщика (path+method), сверить request (потребитель ⊆ принимает поставщик), response (поставщик ⊇ ожидает потребитель), коды и content-type.
- [ ] Единый `ValidationError` + JSON-отчёт в общем формате (см. E0).
- [ ] CLI `validate contract-tests.yaml` + exit codes, как в async.

**Артефакты проектирования (skill `program-design`, этап 2):** `docs/design/contract-validate/` — `intent.md`, `slices.md`, `messages.md`, `slices/01-…`, `contracts-graph.md`, `backlog.md` с handoff-чеклистом.
**DoD MVP:** пара совместима/несовместима определяется корректно; компонентные тесты CLI зелёные; отчёт в общем формате; README по скиллу `documentation`.

## E2 — pinout-netlist: координатор графа и детект breaking-change

**Статус:** 📋 каркас + пакет проектирования созданы (этап 3); реализация после MVP E1.
**Цель:** хранить граф consumer↔provider, версии контрактов, принимать отчёты валидаторов, детектить breaking-change во времени.
**Зависит от:** общий формат отчёта (E0/E1).

- [ ] Модель данных: сервис, спека+версия/коммит, ребро consumer→provider, запись вердикта.
- [ ] Приём отчётов от async/openapi валидаторов.
- [ ] Диф контракта поставщика против предыдущей версии → влияние на живущих потребителей.
- [ ] Запрос «кто сломается, если поставщик так изменит контракт».
- [ ] (Позже) визуализация графа зависимостей.

**DoD MVP:** netlist принимает отчёт обоих валидаторов и строит граф пар; диф двух версий спеки поставщика помечает затронутых потребителей.

## E3 — pinout-cli: единый фронт

**Статус:** 📋 позже.
**Цель:** одна точка входа для разработчиков и CI поверх валидаторов и netlist.
**Зависит от:** E1, E2.

- [ ] Делегирование `validate` нужному валидатору по типу взаимодействия.
- [ ] Команды работы с netlist (push отчёта, запрос графа/impact).

## E4 — service-template: скилл `component-tests` от спеки поставщика

**Статус:** 📋 методология, параллельно. **Upstream-репозиторий** [service-template](https://github.com/ubik-life/service-template/).
**Цель:** доработать существующий скилл `component-tests` так, чтобы у потребителя сценарии **и** заглушки выводились из master-спеки поставщика, на контракт которого он опирается.

- [ ] Расширить процедуру: вход — спека поставщика; happy path + сценарий на каждый обещанный контрактом режим отказа.
- [ ] Конвенция генерации contract-true заглушек из master-OpenAPI поставщика.
- [ ] Изоляция фикстур по slice сохраняется (без скрытой связности).

**DoD:** скилл генерирует сценарии и заглушки из спеки поставщика; согласован с моделью контракта pinout.
